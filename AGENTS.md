# AGENTS.md

This is a Godot 2D space shooter game being developed inspired by the early 1980s game "Galaga" by NAMCO for the MSX home computer.

## Requirements

- Godot 4.7 using GDScript and following Godot's own code style guidelines.

## Testing

All **gameplay** testing is manual by the human after every iteration: do not run the main game scene.
The testing device is:

1. Samsung Odyssey laptop running Omarchy Quattro in 1920 x 1080 @ 60 Hz.

## Agent Workflow Notes

- While the agent writes files, keep those files **closed** in the Godot script editor: an open buffer can silently revert external writes on focus/undo/save.
- After every script write, **read the file back from disk** — never trust the write receipt alone.
- `node_set_property` cannot coerce strings to bool/int — set non-string properties in GDScript instead.
- `input_map` calls must be **sequential** (parallel bursts wedge the backend lock); `project_manage settings_set` accepts invalid keys without complaint (verify setting names against engine docs).
- Godot 4 API differs from Godot 3 memory (e.g. `ScrollContainer.horizontal_scroll_mode`). When unsure about a property or method, check the Godot 4.7 docs instead of guessing.
- Editor-log ghosts: the log buffer re-emits stale diagnostics on scans — confirm errors against current file contents (grep) before treating them as live.
- Never reference `EditorInterface` directly from a script that is shipped in a game: editor classes are stripped from export templates and the script then fails to load. Access it only under `Engine.is_editor_hint()` through `Engine.get_singleton(&"EditorInterface")`.
- Godot generates `.gd.uid` sidecars; keep them tracked so scenes and references stay stable.
- `Entity` origin sits at the **center** of its shape (both axes), and the shapes are built in `_refresh_shape()`. Hand-placed entity positions assume that: changing the shape offset means shifting `y` by `Helpers.ENTITY_HALF_WIDTH * scale_aux` in the scenes, or the visual moves.
- Physics layers live in `PhysicsLayers` and are assigned by `Entity._apply_layers()` from `data.team`, not in scenes. For each pair of interacting things, exactly one side lists the other in its mask (otherwise every hit fires twice): foes mask `FRIEND` for ramming, projectiles are the monitoring side.
- A foe's `global_position` and `rotation` belong to its `FoeBrain` child, never to an `EntityController`; `Entity` leaves uncontrolled entities alone, so do not give a foe a controller.
- `Weapon` is a child node of the shooter and stays team-agnostic (the projectile takes the shooter's `data.team`). `Projectile`s are built in code and spawned into the node in the `projectiles` group; the projectile is the monitoring side, so its mask lists the target Entity layer and Entities never list projectile layers. A successful shot calls `Entity.play_fire_feedback()`, which pulses the sprite when `fire_pulse_enabled` is on and shakes the camera only when `shake_on_fire_enabled` is on too, so fire feedback is per `EntityData`, not per team.
- Entry paths are shared `Curve2D` resources under `resources/curves/`, wrapped in a `Path2D` in the level so they can be reshaped in the editor; gameplay reads the curve, never the `Path2D`.
- `FoeBrain`s register in the `foe_brains` group; a `DiveDirector` in the level decides who dives and when (`FoeBrain` never schedules its own dives). Dive curves live on `WaveData.dive_curves`, the only source of truth (`DiveDirector` has none of its own); a foe picks one at random per dive, and curves are anchored at the foe's position at dive start, so one curve serves every slot.
- Formations are built once per `FormationData` per stage and never rebuilt or freed mid-stage: `StageDirector` owns them under the level's `Formations` node, caches one instance per distinct (`FormationData`, `WaveData.sway_start_phase_deg`) pair (waves sharing both sway in unison; a different phase gets its own instance, whose duplicated grid can cross it), and only frees them when the next stage begins. The slot a foe receives in `FoeBrain.setup()` is therefore valid for the foe's whole life, and a foe never looks its slot up again. The sway phase starts the sine (`Formation.sway_phase`, radians, set before the node enters the tree): 0 is the centre moving right, 90 the right edge, 180 the centre moving left, 270 the left edge.
- A `FormationData` may define its shape with a `layout` PNG (one pixel = one cell, alpha above 0.5 = slot, keep the import Lossless): the image size replaces `columns` / `rows` and its center is the formation center. `Formation.get_slot()` returns `null` for a hole, and waves still fill one row each, only its occupied columns. Cells keep their pixel color on the `FormationData` for future foe groups; nothing reads that color yet.
- **Wave firing**: `WaveData.fire_on_entry` / `fire_in_formation` reach each foe through `FoeShooter.configure(wave)`, which `StageDirector` calls right after `brain.setup()`. Entry fire is local to the foe and only counts from `ENTERING`/`SETTLING` until the foe's **first** arrival in formation, so a foe settling back after a dive never fires for that reason. Formation fire is scheduled by the level's `FireDirector` (a `FoeShooter` never schedules it itself): it picks a random foe of a wave with the flag on, at its own interval, and only starts a shot while the live foe-team projectiles are below its cap (dive and entry shots ignore the cap). Formation fire stops by itself when no capturable hero exists, which keeps the respawn rule satisfiable.
- Gameplay logic can be checked headlessly without opening the game: run a throwaway `extends SceneTree` script with `godot --headless --path . --script res://tools/name.gd`, instantiate the level there, then delete the script.

- **Fleet**: `Universe` owns a `Fleet` (a plain `Node` in the `fleet` group) that owns one or two hero `Entity`s: it sets their **global** positions, clamps the block by the combined width and calls `Entity.drive()` on each, so both move and fire as one. Members have no effective controller (`Entity.externally_driven`). Lives are `GameManager.reserve_ships` (the HUD icons) plus the ships in play: losing one of two changes nothing, and a reserve ship is spent only when the fleet empties (or the game ends). A ship grabbed by a beam leaves the fleet; the survivor keeps its x and becomes the leader in place. The dock side is whichever position fits and is closest to the freed ship. A freed ship (`Entity.begin_return()`) is `returning` (no input, no damage, `is_capturable()` false) and the `Fleet` flies it to its slot — or to `HeroSpawn` when the fleet is empty — in `RETURN_DURATION`, which replaces the respawn delay at no life cost. While it flies, `Universe` freezes `$Entities`, `$Projectiles`, `$Formations`, `$DiveDirector`, `$FireDirector` and `$StageDirector` with `process_mode`, so backgrounds, effects, HUD and audio keep running. `Entity.is_capturable()` is the single filter for beams, foe aim and rescue.
- **Tilt**: geometric roll of the polygon points (`Helpers.roll_polygon`) driven by measured horizontal velocity projected on the entity's lateral axis (`cos(global_rotation)`). The collision polygon follows only when `tilt_affects_collision` is on; quantized to 24 steps so rebuilds are rare. No shader is used.
- **Trail**: ghosts copy `visual.global_transform` (including roll), are inserted just behind the entity in the parent, fade out over `trail_lifetime`, and use `data.trail_alpha`.
- **Tractor beam**: The capture lock lives on `FoeBrain._capturer` (validated with `is_instance_valid`); the life is committed only when the carrier reaches formation (`Carry.COMMITTED`), while before that the hero is only "parked" (hidden, frozen, non-monitorable). A released ship calls `begin_return()` and `FoeBrain` looks up the `fleet` group to `recruit()` it; a committed capture frees the old hero and `recruit_new()` spawns its replacement at the rider. The beam (`TractorBeam`) is the monitoring side of the physics layers (`collision_mask = FRIEND`, `monitorable = false`), and the rider (`Polygon2D`) is top-level and follows the foe (`rotation = foe.rotation + PI`). No capture sound or effect plays until the beam actually captures (`get_touching_hero()`), and `FoeBrain` only creates the `TractorBeam` node when `data.tractor_beam_enabled` is true.
- **Dash**: the dash lives in `DashAbility` as a child of an Entity with `dash_enabled`; the leader's ability moves the whole fleet through `Fleet.move_block`; a dashing Entity is `invulnerable` and is ignored by ramming, projectiles (they keep flying) and tractor beams; and the alpha cue is applied every frame to the visual's `modulate.a`.
- **Weapons**: an Entity may carry several `Weapon` children, collected by `Entity` into `weapons` keyed by `Weapon.weapon_id`; the first `Weapon` child is `Entity.weapon`, the primary that foes, bosses, `FoeShooter`, `BossPattern` and the tractor beam keep using unchanged. Firing goes through `Entity.drive_weapon(id, fallback_id)`: `id` fires when `Weapon.can_fire()` (data set, owner ready, `_in_flight < max_in_flight`), otherwise `fallback_id` fires when given. `Weapon.override_color` false keeps `ProjectileData.color` instead of the shooter's colour.
- **Fire requests**: `PlayerController` (physics priority -10, `PROCESS_MODE_ALWAYS` so a release while paused cancels) caches one `get_fire_request()` per physics frame plus `get_charge_progress()` / `is_charge_ready()`; `Fleet` fans the request and charge state out to every ship in `Fleet._physics_process`, and a lone Entity reads its own controller in `Entity._physics_process`. Other controllers keep the `EntityController` default (`&"primary"` when `wants_fire()`). `drive(wants_fire)` stays for compatibility; firing while dashing is still allowed.
- **Charge**: configured by the `Charge` exports of `EntityData` (`charge_enabled`, `charge_time`, `charge_weapon_id`, shake/ring/particle tuning); the state machine lives in `PlayerController` (fresh `fire` press to start, release fires the charge weapon when ready else the primary, cancel on death/capture/`returning`/rescue freeze/stage change/game over, never on dash, signals `charge_started`/`charge_ready`/`charge_cancelled`/`charge_released`). Each ship shows its own `ChargeEffect` child at the charge weapon's `get_muzzle_local()` (pooled code-drawn particles converging on the muzzle) and shakes only its `visual` in x, restored to `_visual_base_position` (set in `_refresh_shape`) at progress 0; ghosts subtract that shake in `_spawn_trail`.
- **Combos**: author a `ComboData` (`resources/combo_data.gd`: `id`, `steps` of Input Map actions, `max_step_delay`, optional per-gap `step_delays`, `min_step_delay`, `strict`, `weapon_id`, `cooldown`) and list it in `EntityData.combos`; `ComboDetector` (owned by `PlayerController`) watches the union of the steps once per physics frame, returns the completed combo, and the controller fires its `weapon_id` with no fallback while consuming the final press. `left`/`right`/`dash` are never monitored, so they never break a combo; `EntityData.validate_charge` (called from `Entity._ready` in debug builds) warns on bad charge/combo config, and `input_debug` prints combo steps and charge events to tune the delays.
- **Drift**: with `EntityData.drift_enabled`, a controller-driven Entity keeps sliding after lateral input ends; `drift_distance_ships` authors the slide from full speed to rest in ship widths (constant deceleration `top_speed^2 / (2 * distance)`, trapezoid integration, so the distance is frame-rate independent). The state lives in the `LateralMotion` component (`scripts/lateral_motion.gd`): while input is held it reproduces today's movement exactly (no ramp, instant reversal), and the edge clamp zeroes the velocity via `report()`. It is wired in `Entity._physics_process` for a lone ship and in `Fleet._physics_process` for the whole block (one instance, parameters read from the leader's data each frame); the velocity resets on death, capture/freeze, rescue flight, `externally_driven` takeovers, dashing, stage change and game over, and `_update_motion_feedback` (tilt and ghost trail) is untouched, so the slide keeps tilting and spawning ghosts. Path-following foes (`FoeBrain`, `BossPattern`) do not use it. `validate_drift` (from `Entity._ready` in debug builds) warns on a non-positive distance or a stopping time above 1 s.

## Commit Convention

When there are changes to commit, AI agents should suggest an one-line commit message at the end of their response following conventional commit format: `type(scope): description`. Use types like `feat`, `fix`, `refactor`, `docs`, `chore` and keep descriptions concise but descriptive — focus on the "why" rather than the "what". This message must be in own line to facilitate copying.
